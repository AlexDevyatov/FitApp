# Логи: как читать инцидент в FitApp

Логи расставлены по критическим путям, чтобы на вопрос «почему так вышло» отвечал
`adb logcat`, а не догадки. Каждый путь пишет свою область под отдельным тегом,
поэтому инцидент разбирается фильтром, а не чтением всего журнала.

## Теги

| Тег | Что пишет | Типичный вопрос |
|---|---|---|
| `FitAppApp` | запуск процесса, выбранный анализатор, необработанные исключения | «приложение закрылось», «попал ли MockAnalyzer в сборку» |
| `FitAppUI` | действия пользователя: съёмка, галерея, анкета, карточка, навигация | «нажал — ничего не произошло» |
| `FitAppPhoto` | сохранение и сжатие снимка, постановка в очередь | «снимок не появился в ленте» |
| `FitAppData` | Room и репозитории: создание карточки, статусы, разбор, правки, удаление | «карточка пустая», «правка не сохранилась», «пропала история» |
| `FitAppKey` | наличие ключа в хранилище, проверка провайдером | «ключ не принимается» |
| `FitAppAI` | запрос, HTTP-код и время, `finish_reason`, `usage`, исход разбора и текста | «модель не ответила / ответ обрезан» |
| `FitAppWorker` | очередь, попытки, ретраи, остановка работы | «снимок висит в обработке» |
| `FitAppReport` | входные числа отчёта, вердикты, источник текста (LLM/fallback) | «отчёт пустой или странный» |
| `FitAppPush` | планирование пуша, срабатывание, разрешение, показ уведомления | «вечерний пуш не пришёл» |

Уровни: `I` — нормальный ход событий, `W` — подозрительное, но не смертельное
(пропуск, повтор, fallback), `E` — операция не выполнена.

## Что в логи не попадает

- API-ключ: ни целиком, ни частично, ни в заголовке `Authorization` — только
  «найден / нет» и результат проверки.
- Байты снимка и тело ответа модели целиком: только размеры и короткие выдержки
  (до 240 символов) в местах, где разбор уже сломался.
- Анкетные числа (пол, возраст, рост, вес) пишутся в `FitAppData` при сохранении
  цели: без них нельзя проверить расчёт TDEE. Журнал остаётся на устройстве.

## Рецепты logcat

```bash
adb logcat -c                                   # очистить буфер перед воспроизведением
adb logcat -s FitAppApp FitAppKey FitAppPhoto FitAppData FitAppUI
adb logcat -s FitAppAI FitAppWorker             # разбор фото
adb logcat -s FitAppReport FitAppPush           # отчёт и вечерний пуш
```

Один снимок по цепочке (по mealId, который печатает `FitAppPhoto`):

```bash
adb logcat -s FitAppPhoto FitAppWorker FitAppAI | grep <mealId>
```

Сохранение в файл и падение приложения:

```bash
adb logcat -d > logcat.txt
adb logcat -b crash -d
```

Фильтр в Android Studio Logcat: `tag:FitApp*` — все области сразу, либо
`tag:FitAppWorker` — только очередь.

## Как выглядят типовые инциденты

**Снимок не появился в ленте.** `FitAppUI` → `capture: кадр получен`; `FitAppPhoto`
→ `сжатие ... in_bytes/out_bytes`, `сохранено`; `FitAppData` → `создана карточка
PENDING`. Если цепочка оборвалась — в логе есть `E` с исключением и тем шагом,
который не прошёл.

**Снимок висит в обработке.** `FitAppWorker` → `поставлен в очередь (KEEP) work_id=…`,
затем `старт разбора, попытка N из 5`. Нет `старта` — работа ждёт сети или стоит
за семафором (не больше двух разборов одновременно). Есть `остановлен системой` —
карточка могла остаться в `RUNNING`.

**Карточка пустая или «Ошибка».** `FitAppAI` → `completion finish_reason=…`,
`image_tokens`, `reasoning_tokens`, `answer_chars`; `outcome …`; `FitAppData` →
`разбор сохранён … items=…` или `FAILED code=…`. `finish_reason=length` при
`reasoning_tokens`, близких к `max_tokens`, — обрыв по бюджету ответа.

**Ключ не принимается.** `FitAppKey` → `check: старт`, `probe: … http=…`;
`FitAppAI` → `outcome auth_error` или `permanent`. `TLS` в тексте — проблема
сертификата, а не ключа (§11 PLAN).

**Настройки открылись, а ключа нет.** `FitAppKey` → `зашифрованное хранилище
не открылось — сбрасываем ключ`, затем `хранилище сброшено, API-ключ нужно
ввести заново`. Keyset в prefs не расшифровывается мастер-ключом устройства
(перенос данных, сброс Keystore): хранилище пересоздано, экран настроек
не падает, ключ вводится заново.

**Пуш не пришёл.** `FitAppPush` → `PeriodicWork 24ч поставлен, первый запуск через
N мин`; вечером — `evening: старт`, затем одна из причин пропуска: пуш выключен,
карточек нет, нет `DONE`-карточек, нет разрешения `POST_NOTIFICATIONS`.
`FitAppData` → `settings: push_hour=…, push_enabled=…`.

**Отчёт за прошлый день показывает сегодняшний.** `FitAppUI` → `nav: дата маршрута
не разобрана` — аргумент навигации пришёл мусором.

**Пропала история.** `FitAppData` → `db: создана с нуля` — база пересоздана
(переустановка или очистка данных), либо `db: база открыта` с ожидаемым путём.
