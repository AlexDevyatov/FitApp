# FitApp — план и архитектура MVP

Дневник питания для Android: снимок еды → разбор моделью → карточка → вечерний отчёт.
Документ фиксирует решения, принятые в гриллинге, и факты, проверенные живыми запросами к провайдеру.
Код пишет владелец проекта; здесь только то, что нужно, чтобы писать его без переделок.

---

## 1. Границы MVP

**Входит**

- онбординг: API-ключ (BYOK) + анкета + расчёт цели по калориям;
- съёмка камерой и выбор из галереи;
- три типа кадра: готовое блюдо, тарелка с несколькими блюдами, упаковка с этикеткой;
- классификация типа кадра моделью (без выбора режима пользователем);
- разбор кадра в структурированные данные и карточка дня;
- правка карточки: название блюда, тип кадра, удаление (цифры — только чтение);
- очередь обработки с ретраями и видимым статусом;
- дневной отчёт: три блока + один вердикт, диапазонная оценка, пометка «мало данных»;
- локальный календарь прошлых дней и тренд;
- вечерний пуш;
- локальный счётчик правок на скрытом экране (без отправки).

**Не входит**

- аккаунты, синхронизация, сервер, веб;
- демо-режим и бесплатные снимки;
- ввод веса порции и ручной КБЖУ-калькулятор;
- вода, БЖУ-графики по нутриентам внутри дня, недельные отчёты;
- монетизация, подписка внутри приложения;
- iOS, планшетные раскладки;
- дисклеймер и ограничения формулировок (решение владельца, см. риски).

## 2. Дерево решений

| # | Ветка | Решение | Следствие |
|---|---|---|---|
| 1 | Пользователь | Худеющий, не желающий считать вручную | Отчёт = дефицит и перекосы, а не «здоровое питание» |
| 2 | Что в кадре | Блюдо, тарелка, этикетка — все три в MVP | Три промпта, три схемы, три класса ошибок |
| 3 | Точность | ±30%, без ввода веса | Отчёт диапазоном, тренды вместо граммов |
| 4 | Доступ | BYOK, без демо, без сервера | Барьер входа, ответственность юзера за ключ |
| 5 | Стек | Kotlin + Jetpack Compose | CameraX, WorkManager, Room — родные API |
| 6 | Отчёт | Экран-сводка + пуш в 21:00 | Ритуал конца дня как механизм удержания |
| 7 | Хранение | Только локально | Нет бэкенда и утечек; потеря телефона = потеря дневника |
| 8 | Момент вызова | Сразу при снимке | Видна ошибка распознавания, пока помнишь контекст |
| 9 | Сбой сети | Очередь WorkManager + ретрай + статус | Снимок не теряется молча |
| 10 | Правки | Название, тип, удаление; цифры только смотреть | Ловит грубые ошибки vision |
| 11 | Ключ | Вставка из буфера + импорт из файла + проверка | Без проверки половина отзывов была бы «не работает» |
| 12 | Метрики отчёта | Ккал, белок, жиры, углеводы, клетчатка/овощи, сахар/упаковка, время | В UI сгруппированы в три блока |
| 13 | Классификация кадра | Модель сама; при сомнении — «блюдо» | Тип правится вручную (см. 10) |
| 14 | Дисклеймер | Нет | Принятый владельцем риск, см. §12 |
| 15 | Телеметрия | Нет; локальный счётчик правок | Метрика читается только на устройстве тестера |
| 16 | История | Календарь + тренд | Отдельный экран и запросы по диапазону дат |
| 17 | Источник фото | Камера + галерея | Два пути в один пайплайн |
| 18 | День | Календарный, с пометкой «мало данных» | Пропуски не выглядят как дефицит |
| 19 | Цель | Анкета → TDEE, дефицит 15–20% | Экран онбординга и формула на продукте |
| 20 | Отчёт считает | Код; LLM только формулирует | Цифры воспроизводимы, токены на текст |
| 21 | Модель | `qwen4-max` | Проверено запросом, см. §4 |
| 22 | TLS | CA в системное хранилище эмулятора | На реальном устройстве может не пройти, см. §12 |

## 3. Технические умолчания

Приняты без обсуждения, меняются одной правкой:

- `minSdk 26`, `targetSdk 36`, JDK 21 (уже стоит, см. `ANDROID_SETUP.md`);
- идентификатор приложения `ru.fitapp`, интерфейс на русском, Material 3;
- ключ — `EncryptedSharedPreferences` (`androidx.security:security-crypto`);
- настройки — `DataStore` (время пуша, цели, флаги);
- фото — JPEG, длинная сторона ≤ 1024 px, качество 80 (≈150–250 КБ → ≈200–330 КБ в base64);
- формула TDEE — Mifflin–St Jeor, коэффициент активности 1.2/1.375/1.5/1.725;
- белок — 1.6 г на кг массы тела, жир — 27% калорий, углеводы — остаток;
- порог уверенности классификации — 0.5; ниже — тип «блюдо»;
- пуш — `PeriodicWorkRequest` 24 ч с начальной задержкой до 21:00 (дрейф до нескольких минут приемлем).

## 4. Провайдер: проверенный контракт

Проверено на живом ключе из `.env` (в документ и в репозиторий ключ не попадает).

```
base_url : https://token-plan.maas.qwencloudapi.com/compatible-mode/v1
модель   : qwen4-max
API      : OpenAI-совместимый (chat/completions), синхронный
TLS      : цепочка подписана локальным CA, не публичным
```

### 4.1. Что проверено

| Запрос | Результат |
|---|---|
| `GET /models` | `200`, 22 модели |
| `qwen-image-3.0-pro` + текст | зависание >60 с, ответа нет — это генератор изображений |
| `qwen3.7-max` + `image_url` | `400 Unexpected item type in content` |
| `qwen4-max` + `image_url` | `200`, разбор тарелки, `usage` с `image_tokens` |
| `response_format: json_schema` (strict) | `200`, ответ ровно по схеме |
| Расход | 782 токена на кадр: 258 картинка, 194 текст, 208 reasoning |

Модель `qwen-image-3.0-pro`, на которую рассчитывал владелец, **не принимает изображения**. Вижн доступен на `qwen4-max`.

### 4.2. Запрос

```bash
curl -sS -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d @request.json \
  https://token-plan.maas.qwencloudapi.com/compatible-mode/v1/chat/completions
```

```json
{
  "model": "qwen4-max",
  "messages": [{
    "role": "user",
    "content": [
      { "type": "text", "text": "<промпт>" },
      { "type": "image_url", "image_url": { "url": "data:image/jpeg;base64,<...>" } }
    ]
  }],
  "response_format": { "type": "json_schema", "json_schema": { "name": "frame", "strict": true, "schema": { "...": "§4.3" } } },
  "max_tokens": 600
}
```

Требования, выясненные на ошибках:

- `content` обязан быть **массивом** частей: строка даёт `400 Input should be a valid list`;
- допустимые типы частей: `text`, `input_audio`, `image_url`, `video_url`, `video`, `file` — всё остальное `400`;
- в ответе есть `message.reasoning_content` — его нужно игнорировать, JSON лежит в `message.content`;
- `finish_reason` бывает `stop` и, вероятно, `length` — при `length` JSON невалиден, это ошибка обработки, а не успех.

### 4.3. Схема ответа (strict)

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["kind", "items", "confidence", "notes"],
  "properties": {
    "kind": { "type": "string", "enum": ["dish", "plate", "label", "not_food"] },
    "confidence": { "type": "number" },
    "notes": { "type": "string" },
    "items": {
      "type": "array",
      "items": {
        "type": "object",
        "additionalProperties": false,
        "required": ["name", "grams", "kcal", "protein_g", "fat_g", "carbs_g", "fiber_g", "sugar_g", "ultra_processed"],
        "properties": {
          "name": { "type": "string" },
          "grams": { "type": ["number", "null"] },
          "kcal": { "type": "number" },
          "protein_g": { "type": "number" },
          "fat_g": { "type": "number" },
          "carbs_g": { "type": "number" },
          "fiber_g": { "type": "number" },
          "sugar_g": { "type": "number" },
          "ultra_processed": { "type": "boolean" }
        }
      }
    }
  }
}
```

Для `label` значения в `items` относятся к съеденной порции; `grams` — оценка веса упаковки, `null` если не видно. Для `not_food` массив `items` пустой, карточка помечается ошибкой и предлагается удалить.

### 4.4. Коды ошибок и что с ними делать

| Ответ | Причина | Поведение |
|---|---|---|
| `401 invalid_api_key` | ключ неверен/просрочен | статус `AUTH_ERROR`, экран настроек, без ретраев |
| `400` | битый запрос или схема | статус `FAILED`, показать текст ошибки (это баг, не сеть) |
| `429` | лимит | ретрай с `Retry-After`, затем экспоненциальный backoff |
| `5xx`, таймаут | провайдер | экспоненциальный backoff, 5 попыток |
| TLS-ошибка | неизвестный CA | отдельный статус с подсказкой про сертификат |

Один кадр = один запрос. Батчинг не делаем: ошибка одного снимка не должна блокировать остальные.

## 5. Архитектура приложения

Один модуль `:app`, пакеты по слоям; выделение в модули — после того как заработает первый срез.

```
ru.fitapp
├── ui/            Compose-экраны, тема, навигация
│   ├── onboarding/  ключ, проверка, анкета
│   ├── day/         лента карточек «сегодня»
│   ├── capture/     CameraX, галерея
│   ├── meal/        карточка, правка
│   ├── report/      отчёт дня
│   ├── calendar/    прошлые дни, тренд
│   └── settings/    ключ, пуш, цели, статистика теста
├── domain/        чистые модели и правила: отчёт, TDEE, диапазоны
├── data/
│   ├── db/        Room: сущности, DAO, миграции
│   ├── files/     хранение фото в filesDir/meals
│   └── prefs/     DataStore, EncryptedSharedPreferences
└── ai/
    ├── DishAnalyzer.kt      интерфейс
    ├── QwenAnalyzer.kt      реализация
    ├── MockAnalyzer.kt      детерминированные ответы для тестов
    └── FrameSchema.kt       JSON-схема и DTO
```

Ключевые контракты:

```kotlin
enum class FrameKind { DISH, PLATE, LABEL }

data class AnalyzedItem(
    val name: String, val grams: Double?,
    val kcal: Double, val proteinG: Double, val fatG: Double, val carbsG: Double,
    val fiberG: Double, val sugarG: Double, val ultraProcessed: Boolean,
)

data class AnalysisResult(
    val kind: FrameKind, val items: List<AnalyzedItem>,
    val confidence: Double, val notes: String,
)

sealed interface AnalyzeOutcome {
    data class Ok(val result: AnalysisResult) : AnalyzeOutcome
    data class AuthError(val message: String) : AnalyzeOutcome
    data class Retryable(val reason: String) : AnalyzeOutcome
    data class Permanent(val reason: String) : AnalyzeOutcome
}

interface DishAnalyzer {
    suspend fun analyze(jpeg: ByteArray): AnalyzeOutcome
    suspend fun probeKey(): Boolean   // GET /models, проверка ключа в онбординге
}
```

`DishAnalyzer` — единственная точка, знающая про провайдера. `QwenAnalyzer` и `MockAnalyzer` подменяются в тестах без сети.

## 6. Модель данных (Room)

```sql
profile(id INTEGER PK CHECK(id = 1), sex TEXT, age INT, height_cm INT, weight_kg REAL,
        activity REAL, deficit_pct INT, target_kcal INT, target_protein_g INT,
        target_fat_g INT, target_carbs_g INT)

day(date TEXT PK, note TEXT, hand_edited INT DEFAULT 0)

meal(id TEXT PK, date TEXT, taken_at INTEGER, kind TEXT, status TEXT,
     photo_path TEXT, confidence REAL, raw_json TEXT,
     error_code TEXT, error_message TEXT, model TEXT, attempts INT DEFAULT 0,
     edited INT DEFAULT 0)

item(id TEXT PK, meal_id TEXT, ord INT, name TEXT, grams REAL NULL,
     kcal REAL, protein_g REAL, fat_g REAL, carbs_g REAL,
     fiber_g REAL, sugar_g REAL, ultra_processed INT)

edit(id TEXT PK, meal_id TEXT, field TEXT, before TEXT, after TEXT, at INTEGER)
```

`status`: `PENDING`, `RUNNING`, `DONE`, `FAILED`, `AUTH_ERROR`, `NOT_FOOD`.
Фото лежат в `filesDir/meals/<mealId>.jpg`; в БД только путь — так проще чистить и бэкапить.
`day.hand_edited` — день, где юзер правил карточки; нужен для честного тренда.
`edit` — источник локальной метрики правок.

Индексы: `meal(date, taken_at)`, `item(meal_id)`, `edit(meal_id)`.

## 7. Промпты

Один системный префикс на все типы кадров + инструкция по типу. Тип кадра заранее не известен, поэтому классификация идёт тем же вызовом.

**Системная часть**

> Ты анализируешь фотографию еды для дневника питания. Определи тип кадра: `dish` — одно блюдо или продукт, `plate` — тарелка с несколькими компонентами, `label` — этикетка или упаковка с составом, `not_food` — на фото нет еды. Разбей кадр на компоненты и для каждого оцени вес в граммах и пищевую ценность съеденной порции. Для этикетки бери данные из состава, а не угадывай. Не занижай калорийность соусов, масла и обжарки. Уверенность `confidence` — честная вероятность того, что разбор верен. `notes` — одна короткая фраза о том, что может быть оценено неверно. Отвечай только JSON по схеме.

Запрещено в промпте: любые медицинские утверждения, диагнозы, советы. Разбор — только измерения.

Промпт отчёта (§8) получает уже посчитанные числа и пишет текст, не выполняя арифметику.

## 8. Расчёт цели и отчёта

### 8.1. Цель

```
BMR(муж)   = 10*вес + 6.25*рост − 5*возраст + 5
BMR(жен)   = 10*вес + 6.25*рост − 5*возраст − 161
TDEE       = BMR * активность
цель_ккал  = TDEE * (1 − дефицит)      // дефицит 0.15…0.20
```

Порог безопасности: если `цель_ккал < 1200` (жен) / `1500` (муж), поднимаем до порога и показываем пометку в онбординге. Это единственное место, где продукт спорит с пользователем о цифре.

### 8.2. Диапазон вместо точки

Каждая оценка кадра несёт ±30%. По дню:

```
low  = Σ kcal_i * 0.7
high = Σ kcal_i * 1.3
```

Вердикт по энергии:

| Условие | Вердикт |
|---|---|
| `high < цель` | «скорее дефицит» |
| `low > цель` | «скорее перебор» |
| иначе | «в пределах неопределённости» |

Тот же приём для белка и остальных: вердикт выносится, только если весь интервал лежит по одну сторону цели. Иначе честное «не определить».

### 8.3. Три блока отчёта

| Блок | Содержимое |
|---|---|
| Энергия | интервал ккал, цель, вердикт |
| Состав | белок (интервал vs цель), жиры, углеводы, клетчатка/овощи, сахар и ультрапереработанное |
| Режим | число приёмов, время последнего, приёмы после 21:00, самый длинный промежуток |

Плюс статус полноты дня: «мало данных», если `DONE`-карточек меньше трёх или есть `FAILED`.

LLM получает JSON с числами и вердиктами и возвращает 2–3 фразы на блок. Текст не может содержать новых чисел — это проверяется регуляркой на числа перед показом.

## 9. Экраны

| Экран | Содержимое | Готово, когда |
|---|---|---|
| Онбординг: ключ | поле/буфер/файл, кнопка «Проверить», проверка `GET /models` и наличия `qwen4-max` | неверный ключ не пускает дальше |
| Онбординг: анкета | пол, возраст, рост, вес, активность | цель посчитана и показана |
| Сегодня | лента карточек по времени, кнопки «Снять» и «Из галереи» | добавленный снимок появляется сразу со статусом |
| Съёмка | CameraX, превью, подсказка «вся тарелка в кадре» | снимок уходит в обработку без диалогов |
| Карточка | фото, список компонентов, КБЖУ, смена типа, правка названия, удаление | правка сохраняется и помечает `edited` |
| Отчёт дня | три блока + вердикт + «мало данных» | вердикт меняется от данных, а не от текста |
| Календарь | дни месяца с отметкой полноты, тренд по ккал | переход в прошлый день работает |
| Настройки | ключ, время пуша, цели, «статистика теста» | доля правок видна локально |

Навигация: нижняя панель «Сегодня / Календарь / Настройки»; съёмка — FAB.

## 10. Фоновая обработка

```
снимок → сохранить файл + meal(PENDING) → enqueue UniqueWork("meal-<id>")
WorkManager → QwenAnalyzer → item[] + meal(DONE | FAILED)
```

- `Constraints`: `NetworkType.CONNECTED`;
- backoff: экспоненциальный, 30 с, максимум 5 попыток;
- `AUTH_ERROR` и `400` — без ретраев, сразу видимый статус;
- повторный запуск того же `mealId` не создаёт вторую запись (`ExistingWorkPolicy.KEEP`);
- ручной ретрай из карточки сбрасывает счётчик попыток;
- при `FAILED` снимок остаётся на месте: юзер видит фото и причину, а не пустую карточку.

Ограничение: одновременно не больше 2 воркеров (семафор), чтобы не ловить `429` на серии снимков.

## 11. Безопасность и TLS

- ключ хранится в `EncryptedSharedPreferences`, в БД и логах не появляется; в `logcat` запрещено печатать заголовок `Authorization`;
- ключ вводится юзером, в APK его нет — это и есть смысл BYOK;
- `base_url` зашит в приложение, но проверка ключа идёт через `/models`, поэтому ключ от другого шлюза отвергается сразу;
- TLS-цепочка шлюза подписана локальным CA. На эмуляторе CA ставится в системное хранилище (`/system/etc/security/cacerts`), приложение при этом **не** отключает проверку сертификата;
- в релизе никаких `trustAllCerts`, `hostnameVerifier` с `true` и `usesCleartextTraffic`.

На реальном устройстве тот же хост, скорее всего, не пройдёт проверку — это будет выглядеть как «приложение не работает», пока не решён вопрос доверия к цепочке у провайдера.

## 12. Риски

| Риск | Проявление | Что делать |
|---|---|---|
| Витрина подписки и реальные модели расходятся | юзер вводит валидный ключ, а `qwen4-max` в каталоге нет | проверка `/models` на онбординге, понятная ошибка вместо «что-то пошло не так» |
| Медицинские советы при снятом дисклеймере | отчёт предписывает «ешьте меньше», кто-то выполняет | решение владельца; минимальная страховка — запрет медицинских формулировок в промпте |
| Google Play Health-декларация | отказ в публикации приложения про похудение | заполнить декларацию до релиза, не после |
| Локальный CA | на устройстве TLS падает | проверять на эмуляторе; для устройства — публичная цепочка или прокси |
| Оценка по фото систематически занижена | юзер в дефиците, а вес стоит | калибровка на 20 эталонных блюдах, поправочный коэффициент на скрытый жир |
| Потеря телефона = потеря дневника | нет бэкапа | осознанно принято; экспорт — первый кандидат в следующий релиз |
| Задержка модели | снимок «висит» 10–30 с | карточка-скелет сразу, статус вместо спиннера на весь экран |

## 13. Порядок работ

| Шаг | Работа | Критерий готовности |
|---|---|---|
| 1 | Каркас Gradle, Compose, навигация, Room, DataStore | приложение запускается на `FitApp_API37` |
| 2 | Онбординг: ключ, `probeKey()`, анкета, TDEE | неверный ключ не пускает; цель считается |
| 3 | Съёмка CameraX + галерея + сохранение файла и `meal(PENDING)` | снимок появляется в ленте со статусом |
| 4 | `QwenAnalyzer` + WorkManager + статусы и ошибки | на 10 реальных фото есть разбор; 401 и 429 обработаны |
| 5 | Карточка: компоненты, правка названия/типа, удаление, `edit` | правка сохраняется и видна в счётчике |
| 6 | Отчёт: диапазоны, вердикт, три блока, «мало данных», текст от LLM | вердикт меняется от данных; новых чисел в тексте нет |
| 7 | Пуш 21:00, календарь, тренд | пуш приходит; прошлые дни открываются |
| 8 | Полировка: CA на эмуляторе, сжатие, пустые состояния | установка на чистом эмуляторе проходит сценарий за 2 минуты |

Шаги 1–4 — проверка главного риска (разбор фото терпим по качеству и задержке). Если после шага 4 разбор на реальных блюдах бесполезен, дальше идти нет смысла: продукт переделывается, а не полируется.

## 14. Как проверять

- `MockAnalyzer` с фиксированными ответами — для тестов отчёта и вердиктов; расчёт отчёта покрывается unit-тестами на границах интервалов;
- 20 эталонных блюд с известным весом — для замера систематического смещения (не для отчёта в UI);
- прогон на эмуляторе: установка, ключ, три типа кадра, отказ сети, неверный ключ;
- метрика MVP: доля карточек, которые юзер не правил, на скрытом экране; цель — не «идеальная точность», а достаточно хороший разбор, чтобы правки не стали ритуалом.
